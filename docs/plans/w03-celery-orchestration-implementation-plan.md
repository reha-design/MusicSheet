## Goal

Connect registered PostgreSQL jobs to a Celery workflow with six ordered stages, queue routing, bounded retries, cooperative cancellation, stage-attempt records, and progress events. Keep PostgreSQL as the job-state authority and publish events through the existing internal `JobEventStore` interface. Run FastAPI and Celery workers as separate processes from the `services/api` Python 3.13 project so the worker can reuse the existing job, artifact, storage, and event modules without installing model runtimes into the API.

## Approved design decisions

- Put the Celery app, task definitions, and workflow dispatcher under `services/api/src/musicsheet_api/pipeline/`; run them in a separate worker process. This reuses existing repositories and avoids a new cross-package persistence dependency.
- Use `CELERY_BROKER_URL` with Redis DB `/0` and `CELERY_RESULT_BACKEND` with DB `/1`. Continue using `REDIS_URL` DB `/2` for `JobEventStore`; Celery does not use the event Streams. Set `CELERY_VISIBILITY_TIMEOUT` to 3600 seconds by default and pass it to the Redis broker transport; deployments with longer real stage runtimes must tune it and the maintenance stale threshold together.
- Add Celery `>=5.6.3,<5.7` to the Python 3.13 API/worker project; Celery 5.6 is the stable line with official Python 3.13 support.
- Route `DOWNLOAD` and `PREPROCESS` to `cpu_io_queue`, `SEPARATE` and `TRANSCRIBE` to `gpu_ai_queue`, and `POSTPROCESS` and `RENDER` to `cpu_render_queue`. Worker concurrency follows the current architecture spec: 4–8, 1, and 2–4 respectively; worker commands make the actual count explicit.
- Register `start_job` on `cpu_io_queue`, then register stage tasks `download_source`, `preprocess_audio`, `separate_audio`, `transcribe_amt`, `quantize_and_score`, and `render_pdf` on their stage queues. The names match the canonical pipeline spec.
- Queue only a `job_id`. Each stage reloads the job and artifact metadata from PostgreSQL; audio bytes and local paths never enter Celery messages or results.
- Use one registered task per stage in a Celery chain. Each stage handler is an internal protocol; W03 adds no downloader, audio transformation, model inference, quantizer, or renderer. An unregistered production handler fails visibly with stable error code `STAGE_NOT_CONFIGURED`; it must never report false completion.
- Persist every stage execution in the existing `stage_attempts` table. Revision 3 plan review identified a missing durable bound for `start_job` redelivery, so add migration v2 with internal `jobs.start_job_attempts INT NOT NULL DEFAULT 0` and nullable `jobs.workflow_dispatched_at TIMESTAMPTZ`. These fields are worker bookkeeping and do not change the public job representation.
- Allow one initial handler execution plus at most three further executions per stage. Typed transient failures use exponential backoff (`retry_backoff=True`), a 60-second cap, and jitter; worker-loss recovery consumes the same persisted four-attempt budget. Keep late acknowledgements and worker-loss requeue enabled. Each handler attempt is persisted as `RUNNING` before handler code begins. On redelivery, close a leftover `RUNNING` attempt with `status=FAILED, error_code=WORKER_LOST`; if its attempt number is already 4, conditionally mark the job `FAILED` with `WORKER_LOST` and acknowledge without running the handler. Permanent errors and exhausted transient retries similarly move the job to `FAILED` with stable codes and safe public messages. Celery's in-memory retry counter is not the authoritative attempt limit. The four-attempt cap begins after a durable claim: a crash before the claim commits can cause further broker deliveries without incrementing it, while no handler effect or chain publish is allowed before that commit.
- Check `CANCEL_REQUESTED` before each stage and before accepting stage progress. The progress reporter polls job state and raises an internal cancellation signal so a long-running handler can stop at its next progress checkpoint. Persist the job as `CANCELED`, close the current attempt as `FAILED` with `error_code=CANCELED` (the existing attempt schema has no `CANCELED` status), emit the terminal event, and stop the remaining workflow. Every failure transition for start-task exhaustion, stage exhaustion, or workflow publish error must take the job-row lock and permit only `PENDING`, `RUNNING`, or `RETRYING` as source status. If `CANCEL_REQUESTED` committed first, close any open attempt and transition to `CANCELED`; if failure committed first, the later cancellation request sees terminal `FAILED` and returns the existing conflict behavior. Never overwrite a terminal state or a committed cancellation request.
- Update PostgreSQL before publishing a `JobProgressEvent`. Event publication failure is logged generically and does not replace PostgreSQL status or make a completed stage fail.
- Dispatch only after the job (and upload source artifact, when present) is committed. Offload synchronous Celery publishing from async API routes to a worker thread; configure Redis broker producer connection/read timeouts at 2 seconds, at most 3 connection retries, and at most 3 task publish retries (one initial send plus at most three retries). If submission reports failure, atomically change only a still-`PENDING` job to `FAILED` with `DISPATCH_FAILED`; if a worker already claimed it, return its current persisted snapshot instead. A task delivered after the failure transition must see `FAILED` and stop. If the failure transition cannot be saved, return a sanitized `503` containing the stable job ID where the API contract permits; never claim dispatch succeeded or leave the failure unreported.
- Stage handlers must be re-entrant: use the stable `(job_id, stage)` operation key and artifact SHA-256 metadata to detect valid prior outputs. Each task holds a dedicated PostgreSQL session advisory lock for its job/stage while executing. Acquire the lock with blocking `pg_advisory_lock`, so a concurrent duplicate waits instead of being acknowledged and potentially consuming the only recoverable delivery. Once a waiting redelivery acquires the lock, reload state: if the stage has advanced or the job is terminal, return as a no-op; if its previous attempt remains `RUNNING`, close it with `status=FAILED, error_code=WORKER_LOST` and start another attempt only while the four-attempt budget remains. The database releases the session lock when the connection closes after worker loss. Celery delivery is at-least-once; this plan does not claim exactly-once execution or add an outbox. Worker concurrency and PostgreSQL connection capacity must account for duplicate deliveries waiting on dedicated lock connections.
- `start_job` holds a dedicated PostgreSQL session advisory lock for `(job_id, START_JOB)` across claim and chain publishing. Under a short job-row transaction, it claims `PENDING` as `RUNNING` and increments `start_job_attempts`; that transaction must commit before any broker chain publish. A redelivery increments it again only if no stage attempt has begun and `workflow_dispatched_at` remains null. If four prior start attempts have been claimed without a recorded publish or stage attempt, the next delivery conditionally records `FAILED`/`WORKFLOW_WORKER_LOST` and acknowledges without publishing, subject to the cancellation precedence above. If it sees `CANCEL_REQUESTED`, it conditionally marks the job `CANCELED` and emits the terminal event; terminal jobs are no-ops. After a successful chain publication, it records `workflow_dispatched_at`; a loss after that commit but before acknowledgement becomes a no-op on redelivery. A loss after broker acceptance but before that commit can publish a duplicate chain on redelivery, within the four-claimed-attempt bound; stage locks and guarded claims make duplicate chains safe. If chain publishing reports failure, acquire the same job-row lock used by stage claims and conditionally persist `FAILED` with `WORKFLOW_DISPATCH_FAILED` only while no stage attempt has begun, subject to the cancellation precedence above; publish the terminal event best-effort. If a stage has already claimed the job, leave its state untouched. A later accepted chain for a `FAILED` job cannot run a handler.
- Redis/Celery may redeliver indefinitely if a process repeatedly dies before either claim transaction commits; there is no durable counter at that point. W03 therefore adds an internal operator maintenance command that scans for jobs with no PostgreSQL progress for at least twice the configured Redis visibility timeout (default 2 hours) and performs guarded recovery after the operator verifies the worker is no longer active. Recovery conditionally marks the job `FAILED` with `WORKER_PRECLAIM_STALLED`, or `CANCELED` if a cancellation request committed first. Later deliveries see the terminal state and acknowledge. This boundary and the manual recovery steps must be documented in the runbook.

## Interfaces

- `CeleryWorkflowDispatcher.submit(job_id: str) -> None` publishes one `musicsheet.pipeline.start_job` task containing only `job_id`, after database commit. The async API route calls this synchronous method in a thread. The Celery app sets `broker_transport_options` with `visibility_timeout=CELERY_VISIBILITY_TIMEOUT` (default 3600), `socket_connect_timeout=2`, `socket_timeout=2`, and `max_retries=3`, and sets `task_publish_retry_policy` with `max_retries=3` and bounded intervals. The worker's start task creates the ordered six-stage chain. Broker exceptions are handled by the API route as described above.
- `JobRepository.fail_pending_dispatch(job_id: str) -> JobRecord | None` is the API submission failure compare-and-set: it changes only `PENDING` to `FAILED`/`DISPATCH_FAILED`, and otherwise returns the current persisted snapshot. Keep it distinct from the worker's `fail_workflow_dispatch`, which handles a chain publish failure after `start_job` may have claimed the job as `RUNNING`.
- `StageHandler.run(context: StageContext, report_progress: ProgressReporter) -> None` performs one stage. `StageContext` contains the current `JobRecord`, `PipelineStage`, persisted job artifacts, and stable `(job_id, stage)` idempotency key; it contains no raw broker-supplied filesystem path. `ProgressReporter(stage_progress: int) -> None` accepts only integer progress from 0 through 100, checks cancellation before persisting, and selects a fixed user-facing message for the stage. Handlers must call it periodically during long-running work.
- The six Celery stage tasks accept `job_id: str` only and use immutable signatures so a preceding Celery result is not added to task arguments. Stage names and queue assignment are fixed by the workflow builder, not trusted from an API payload.
- `StageAttemptRepository.acquire_stage_lock(job_id, stage, connection) -> None` uses a stable signed 64-bit digest and blocking PostgreSQL `pg_advisory_lock`; the task keeps this dedicated connection until the handler ends. Lock waiters must reload the job and stage state after acquisition before they do any work.
- Internal musicsheet-orchestration-maintenance scan lists nonterminal jobs whose updated_at is older than twice the configured broker visibility timeout, including job ID, status, stage, dispatch count, and latest attempt; it exposes no source URL, path, or driver error. fail-stalled --job-id ID --observed-updated-at TIMESTAMP --observed-status STATUS requires an operator-selected row from that scan, takes the start and current-stage advisory locks with pg_try_advisory_lock, then locks the job row and verifies the exact timestamp, status, age, and eligible state have not changed. If any task lock is held or state changed, it refuses to write and tells the operator to rescan; this includes a cancellation request committed after the first scan. The operator may retry with the new timestamp and status after the stale threshold is met. Otherwise, it closes any open stage attempt and conditionally marks FAILED/WORKER_PRECLAIM_STALLED, or CANCELED when CANCEL_REQUESTED won first, then publishes a terminal event best-effort. This is an internal CLI, not a public endpoint or unattended automatic failure.
- Stage persistence records `RUNNING`, `COMPLETED`, or `FAILED` attempts using the existing schema fields (`id`, `job_id`, `stage`, `attempt`, provider/model version, timestamps, duration, and error fields). Allocate attempt numbers while locking the owning job row. In one job-row transaction, a task claims only its expected stage from `RUNNING` or `RETRYING`, creates the `RUNNING` attempt, and releases the row lock before running the handler; completion/failure updates the attempt and guarded job transition together in another transaction. Retry status is recorded on `jobs`; each actual handler execution creates a distinct attempt row, with `attempt <= 4`. Cooperative cancellation closes the attempt as `FAILED` with `error_code=CANCELED`, then conditionally transitions the job to `CANCELED`. The task also holds a PostgreSQL session advisory lock for its job/stage while the handler executes. If a redelivery obtains the lock and finds a prior `RUNNING` attempt, it closes that row with `status=FAILED, error_code=WORKER_LOST`; it starts another attempt only when the prior attempt number is below 4. Concurrent duplicates wait and cannot execute the handler concurrently. A task for a terminal job or an already-advanced stage acknowledges as a no-op.
- Job progress uses the common `JobStatus`, `PipelineStage`, and `JobProgressEvent`. Overall progress is computed with equal stage weights: `floor((stage_index * 100 + stage_progress) / 6)`, with zero-based stage indices and the final successful stage set to 100.

## Validation and acceptance

- Celery configuration has stable `/0` broker and `/1` result defaults, honors explicit environment overrides, declares the three named queues, and never connects during module import.
- Both job registration routes persist before dispatch, publish only the job ID, and report broker failures without leaving an unobservable pending job. The v2 migration is applied explicitly before worker startup, and v1 schema is rejected safely.
- The workflow contains all six stages in order and routes each to the queue in the canonical architecture spec.
- Every stage attempt and job transition is persisted in PostgreSQL with safe error fields. PostgreSQL remains authoritative if Celery's result backend or Redis event publishing is unavailable.
- Each stage executes its handler at most four times total. Typed transient failures back off with a 60-second cap and jitter; worker-loss requeues after a committed claim consume the same persisted budget and the fourth lost attempt ends in `FAILED`/`WORKER_LOST` on redelivery. `start_job` also has at most four persisted publication attempts; a fifth delivery after four claimed attempts ends in `FAILED`/`WORKFLOW_WORKER_LOST` if no stage has begun. Pre-claim broker deliveries can repeat without consuming a counter, so the internal stale scan and guarded operator recovery provide a visible recovery path. Cancellation wins when its row update commits before failure; failure wins when it commits first, and neither terminal state is overwritten.
- A producer exception after broker acceptance cannot overwrite a worker-claimed job. Stage handlers begin only after an atomic state/stage claim; a delayed chain for a `DISPATCH_FAILED` job performs no handler side effects. Producer socket and retry limits prevent an unbounded API publish wait, and the publish call runs outside the async event loop.
- Valid progress updates persist before event publication and use the existing `JobProgressEvent` contract. Redis errors do not expose sensitive details or corrupt the PostgreSQL status.
- W03 contains no actual media/model/render processing and cannot falsely mark a missing stage handler successful.
- Every implementation task has independent review at 95/100 or higher and no unresolved blocker/important finding; score, date, reviewed range, findings, and disposition are recorded.

## Review focus

- Can a Celery worker import task modules without starting FastAPI or opening connections at import time?
- Can worker-loss requeue recover a task whose previous stage-attempt row is still marked `RUNNING`, while a concurrent duplicate waits on the advisory lock and cannot run the handler concurrently? Does the fourth lost attempt close as `FAILED`/`WORKER_LOST` without another handler execution? Does `start_job` recover safely and stop after four lost publication attempts both before and after chain publication?
- Can a lock waiter or stale retry overwrite a newer stage or a terminal job state after it acquires the lock and reloads current state?
- Does a Redis event failure leave the PostgreSQL update committed and keep the shared API Redis client open?
- Are dispatch failures and retry exhaustion visible to the caller with stable IDs/codes and no raw broker/driver exception details? Is the accepted-then-reported-error race safe, and can a slow broker publish block unrelated API requests?
- Can the maintenance scan detect a job stalled by pre-claim worker loss, and does guarded recovery refuse a live lock, changed observed timestamp or status, or cancellation while allowing later broker redelivery to stop?
